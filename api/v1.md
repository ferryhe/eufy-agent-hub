# Resident recording API v1

Start `npm start` after installing/building the vendor adapter. Configure `EUFY_PYTHON` (Python with PyAV) and `EUFY_FFMPEG` for continuous export. The service listens on `127.0.0.1:3187` by default (`EUFY_PORT` overrides it). Complete the normal CA-region login/challenge flow on `/`; the existing `/login`, `/verify`, `/refresh`, `/logout` and event-recording page routes remain available.

The JSON Schema draft-07 contract is exported by `v1-contract.cjs` and available at `GET /api/v1/contract`. Its named `definitions` validate both requests and responses. Request schemas perform shape validation; the shared [recording time-window contract](../docs/recording-time-window.md) supplies calendar and timezone semantics. Ajv is a direct runtime dependency. HTTP integration tests validate actual response bodies against the same public contract.

New device, range, export and retry operations require a valid resident login. Local job listing/status, cancellation, artifacts and existing request-ID reuse remain available after logout or expiry. Use `Content-Type: application/json` for POST. Browser callers must supply the matching local `Origin`; command-line clients may omit Origin. Host must match the local service address. The page and CLI use this same single-account resident session.

`session.authenticated` reflects the adapter's known token validity. Expiry reports `phase:"login_required"` and returns `UNAUTHENTICATED` for new cloud operations, including a body or inventory request already in flight. `captcha` contains the image only during an image challenge; submit its answer or an email code to `verificationUrl` on the same service. Authentication mutations return `202 {ok:true}` for acceptance; poll session state for their outcome. Passwords and pending challenges are never persisted. The service restores completed sessions before listening, validates cloud inventory and explicitly requires login on failure. See the [auth lifecycle contract](../capabilities/auth/README.md) for persistence and provider limitations.

Logout clears shared cloud credentials and cancels queued jobs with `LOGIN_REQUIRED`. An already-owned capture may finish; a job not yet acquiring capture rechecks login first. Expired queued work exposes `stage:"login_required"` with `LOGIN_REQUIRED`, and cannot start capture. Cancelled request IDs remain bound to their original jobs; use a new ID after login. Logout is admitted during v1 work, while login/verification/refresh retain their final body guards and wait for ownership to settle.

Resident playback owns one dedicated P2P across requests and is mutually exclusive
with exports, range queries and legacy recording work. Logout waits for this owner
to close before clearing the login and returning acceptance; shutdown also waits.
See [playback-session authorization, states and errors](../capabilities/recordings/PLAYBACK_SESSIONS.md).

`GET /api/v1/session` includes a random per-process `residentEpoch`. A direct
historical browser create sets `media:true`, speed 1, a non-empty `requestId`, and
that epoch. Its video-only H.264/HEVC decoder yields at most 5 fps/960 px MJPEG in
memory. Each part binds session/request/media epoch/frame sequence and the honest
`source-received-position` observation; it is not exact JPEG PTS or frame-accurate
seek. Media windows remain 1–60 whole seconds inside one current indexed record.
Pause keeps the existing 30-second lease and freezes output; resume uses a new
decoder epoch. Seek performs confirmed old close/cleanup before new open under one
continuous admission. Control-only callers, including verified legacy speeds
1/2/4/16, remain unchanged and never require a browser consumer.

Live video uses those same resident media guards. New live work conflicts with queued/running exports, playback and range queries; live never preempts them. A live session holds admission through awaited protocol, media-stream and decoder-child cleanup. Logout closes live first; a media-client disconnect or maximum duration also stops it. See [live identity, media access, bounded lifecycle, stable errors and hardware acceptance](../capabilities/live/README.md). `liveVideo` remains `protocol_hint` until exact device/firmware hardware evidence is independently recorded; talkback and RTSP require separate verification.

Example export body:

```json
{
  "requestId": "drive-way-20260827-1630",
  "serial": "<serial returned by devices>",
  "day": "2026-08-27",
  "start": "16:30",
  "end": "16:50",
  "timezone": "America/Toronto"
}
```

For range lookup, omit `requestId` and `serial` (the device serial is in the URL). The service resolves camera → HomeBase → channel from its account inventory. Callers cannot supply a HomeBase conflict key. The existing T8600/T8030 recording path is eligible for execution; this does not assert that every device/firmware has been verified or that every requested interval is complete. A successful range request tests current reachability.

## Device capability queries

Device list, single-device and capability responses include a `discovery` object
alongside the projected data. It reports `status`, `completeness`, `pagination`,
`pagesRead`, `receivedCount`, `uniqueCount`, `limitReached`, `failedPage`,
`retryable`, `stale` and `reasons` (schema definition `discovery`). The production
Mega read remains one request with `num: 100`; continuation is unverified.
Successful empty, short and capped results all have `status: "succeeded"`,
`completeness: "unknown"`, `pagination: "unverified"`. A 200 response never proves
the whole account was enumerated. Raw counts are recorded before serial
deduplication; unknown models remain visible.

Inventory failures return HTTP 503 `DEVICE_UNAVAILABLE` with
`discovery.status: "failed"`, `completeness: "incomplete"`, `retryable: true`
and the failed one-based page. Repeat the request to retry; there is no resume
cursor. A later verification-record/projection failure returns
`CAPABILITY_RECORDS_UNAVAILABLE` with the same failed/incomplete/retryable state,
`failedPage: null` and the successful raw read's counts and limit flag. v1 does
not return cached devices on these failures. The session `/status` and capability
`getDevices`/`refreshDevices` also expose this structure and mark retained old
devices `stale: true`. See the [protocol evidence and precise field semantics](../capabilities/devices/DISCOVERY.md).

Device list and single-device responses expose nullable firmware (`main`,
`secondary`), HomeBase/channel association, raw numeric inventory status, and seven
capability entries: `continuousRecordingQuery`, `continuousRecordingExport`,
`continuousPlaybackControls`, `eventRecordings`, `liveVideo`, `talkback`, `rtsp`. Each capability returns
`{ status, reason, evidence }`; evidence items have `source`, `observedAt` and
`outcome`. The focused capability endpoint returns those same fields plus
`serial` and the requested `capability`. It uses the same login, busy and in-flight
inventory guards as device reads. A device absent from the retrieved subset is
404 `DEVICE_NOT_FOUND` with `discovery`; this does not prove account-wide absence.
An uncatalogued capability is a normal 200 result with status `unknown` and reason
`capability_not_catalogued`.

| Status | Meaning |
| --- | --- |
| `verified` | Dated evidence matches the exact device, model, firmware and participating HomeBase/channel scope |
| `unsupported` | Explicit negative evidence matches that scope |
| `unknown` | No applicable verification or protocol hint; no unsupported claim is inferred |
| `protocol_hint` | A library command or historical model path exists, without current device/firmware verification |

`recordingExport.supported` retains **execution eligibility**. Its `status` now
uses the four-state matrix, so an eligible but unverified pair is `protocol_hint`.
Clients that previously expected only `verified`/`unsupported` must accept the
new states. Unverified live/RTSP/talkback does not prevent eligible recording.
Historical partial export evidence remains `outcome: "partial"`; a verified
capability never changes a partial recording job to succeeded or complete.

`verificationScope` exposes device serial/model/main+secondary firmware, nullable
participating HomeBase serial/model/firmware, and nullable channel.
`verificationHistory` contains observations for that device only, including old
firmware and unresolved scopes. A declared parent absent from inventory leaves
public `homeBaseId: null`, but its identity is preserved in verification scope
with unknown model/firmware. It cannot qualify for current verification. Unknown
main firmware on a participating device never matches as a wildcard, and a
changed device, firmware, HomeBase or channel does not inherit old verification.

Inventory availability is `unknown` unless the eligible path lacks a required
LAN address (`unavailable`). Numeric inventory `status` is preserved as
`state.inventoryStatus`, without guessing its online meaning. An explicit dated
local reachability observation can report `online` or `offline`, with its reason
and date in `state`. The writer owns freshness; it is a last observation rather
than an automatic polling promise. Offline state is separate from capability
support, and a generic range failure returns 503 without inventing unsupported
or offline evidence. Recording attempts still perform their normal transport checks.

The API reads version-1 local evidence from `output/devices/verification.json`.
Use `EUFY_CAPABILITY_RECORDS_PATH` or `createServer({ capabilityRecordsPath })`
to select another path, or inject `deviceRepository`. The
[device repository](../capabilities/devices/README.md#persistent-verification-records)
offers `record(observation)` for authorized future recordings/live writers and
`observeReachability(observation)` for explicit connection observations. Each
write preserves other capabilities/scopes and becomes visible on the next read;
reopening the repository or server retains the same evidence. Missing files mean
no evidence. Corrupt records or unreadable paths return 503
`CAPABILITY_RECORDS_UNAVAILABLE`, preserving the file instead of silently
discarding evidence. Logout keeps evidence but disallows device/capability reads.
There is no public evidence-write HTTP endpoint and no automatic promotion of
anonymous historical camera/HomeBase records by model. See the
[sanitized historical verification record](../capabilities/devices/VERIFICATION.md)
for missing firmware and actual partial-capture limitations.

All recording windows use `normalizeWindow`: IANA timezone, default `EUFY_RECORDING_TIMEZONE` or `America/Toronto`, caller input plus normalized UTC boundaries and timezone. Ambiguous/nonexistent local times are rejected. Start and end must be ordered within the same caller-local day; crossing midnight is rejected, including a different `endDay`. Range responses contain clipped, ordered, non-overlapping index intervals; `coverage:null` explicitly means no footage completeness has been proved. An empty index returns HTTP 200 with `availability:"none"`, `code:"NO_RECORDING"` and `ranges:[]`.

New exports return HTTP 202 with `{job, reused:false}` as soon as the job is durably queued, after device lookup and input validation. No capture, media conversion or full decode is awaited by that HTTP request. `job.jobId` identifies the work and `job.requestId` is globally case-sensitive within the configured durable store. Reusing an existing request ID returns HTTP 200 with the original job and `reused:true`, even when the rest of the supplied input changes or is omitted. It never retries or reinterprets that job. Use a new request ID to request new work.

`GET /api/v1/jobs` discovers every retained job in the resident's authoritative
store, including jobs submitted by the page, CLI or Agent and jobs recovered on
restart. It returns `{jobs,nextCursor}` using the same safe job and artifact
projection as get-by-ID; filesystem paths, session data and unregistered files
are not exposed. Pages are ordered newest first by durable `sequence`, then job
ID as a deterministic tie-breaker. `pageSize` defaults to 25 and accepts 1–100.
Optional `state` accepts `queued`, `running`, `succeeded`, `failed` or
`cancelled`; optional `serial` is the exact camera serial. Unknown, empty,
repeated or malformed parameters return 400 `INVALID_REQUEST`.

`nextCursor` is opaque and must be replayed unchanged with the same state and
serial filters. It is bound to this durable store; malformed cursors, cursors
from another store and cursors combined with different filters return 400
`INVALID_REQUEST`. The first page freezes the traversal's highest durable
sequence. Jobs submitted later are excluded from that traversal, so paging
cannot duplicate or skip retained entries because of concurrent submission;
start a new first-page request to include them. State filtering is evaluated
from each job's current state when each page is read. It is intentionally a live
filter, not a transactional snapshot: a job that changes state between pages may
enter or leave the remaining filtered results. Page reads never submit, retry or
otherwise execute a job.

One resident `ContinuousExportService` owns all accepted jobs. Poll the job endpoint for `queued`, `running`, `succeeded`, `failed` or `cancelled`, plus `stage` and `progress` (0–1). Closing the submitting HTTP connection does not cancel work. Jobs on the same HomeBase serialize. Range lookup, login/refresh and legacy recording operations are mutually excluded from conflicting active v1 work so they cannot replace its session or playback connection. Recovered queued work participates in these same guards.

`POST /api/v1/jobs/:jobId/cancel` with `{}` cancels queued work immediately (HTTP 200) or persists and signals cancellation of running work (HTTP 202). A stopping job remains `running` with a non-null `cancellationRequestedAt`; poll until `cancelled`. The service stops later receive/mux/convert/decode work and waits for owned cleanup before releasing the HomeBase. Repeating cancellation is idempotent while stopping or after cancellation. Successful or failed jobs return 409 `JOB_UNAVAILABLE`. The last stage, progress and partial evidence remain available.

`POST /api/v1/jobs/:jobId/retry` with `{"requestId":"new-unique-id"}` explicitly retries a failed or cancelled job. HTTP 202 returns a new job with the original input, a fresh output directory, `retryOfJobId` pointing to the old job and `attempt` incremented from the old attempt (original jobs use 1). The original job and diagnostics are retained. A retry joins the same HomeBase FIFO behind previously accepted work. The API revalidates login and the current device; if its HomeBase changed, submit a new export after checking the device. Other retry input fields are rejected. Successful or unfinished jobs return 409 `JOB_UNAVAILABLE`.

Request identity is global across export and retry: repeating either operation with an existing `requestId` returns its original job with HTTP 200 and `reused:true`, without execution, including after failure, cancellation or restart. This also applies when a retry ID was originally used by a different job. The retry URL must name an existing source job. Failed jobs never replay implicitly.

After the previous owner and its media processes have stopped, restarting the resident service automatically schedules persisted `queued` jobs in original FIFO order. A previous `running` job becomes `failed` with `JOB_INTERRUPTED` and an actionable reason; its last stage/progress, registered partial artifacts and diagnostics survive. It cannot resume media processing or become successful implicitly. Persisted cancellation intent instead completes as `cancelled` on restart. A recovered queued job without a valid login fails with `LOGIN_REQUIRED` and needs an explicit retry after login. These behaviors keep the existing public terminal states and CLI exit classifications. There are no new CLI commands.

The final `job.result` is the authoritative #7 pipeline result: normalized window, observed raw coverage, completeness reasons, validation, media timing and preserved diagnostics. Only verified complete coverage with full successful decode can produce `state:"succeeded"`. An honest partial recording has `state:"failed"`, `result.outcome:"partial"` and `error.code:"PARTIAL_RECORDING"`; an export failure has `result.outcome:"failed"` and `error.code:"EXPORT_FAILED"`. Reaching an end marker, an exit code of zero or an existing file never supplies API success. The empty-index response above describes source availability; a later capture failure is still a failed job and retains its pipeline diagnostics.

Artifacts list final files, partial files and diagnostics. `playable:true` and `validated:true` mean that particular media passed the pipeline's full decode, not that it covers the whole requested interval; inspect `outcome` as well. A playable partial remains `outcome:"partial"`. Raw/candidate/log artifacts are explicitly `playable:false`, `validated:false`. Only registered files owned by that job are served. Playable MP4s support HTTP Range and `?download`; other artifacts are byte downloads. Never construct an artifact URL from a filesystem path: use the returned URL.

Errors have `{error:{code,message}}` and include `discovery` for inventory-stage failures or a serial absent from the retrieved subset; code is stable while human-readable messages may change. Main HTTP classifications:

| HTTP | Codes |
| --- | --- |
| 400 | `INVALID_REQUEST`, `INVALID_WINDOW`, `INVALID_TIMEZONE`, `AMBIGUOUS_OR_NONEXISTENT_TIME` |
| 401 | `UNAUTHENTICATED` |
| 403 | `LOCAL_HOST_REQUIRED`, `LOCAL_ORIGIN_REQUIRED` |
| 404 | `DEVICE_NOT_FOUND`, `JOB_NOT_FOUND`, `ARTIFACT_NOT_FOUND`, `NOT_FOUND` |
| 409 | `SERVICE_BUSY`, `JOB_UNAVAILABLE` (for example retrying a successful job or cancelling a failed job) |
| 413 / 415 | `INPUT_TOO_LONG` / `JSON_REQUIRED` |
| 422 | `UNSUPPORTED_DEVICE` |
| 503 | `DEVICE_UNAVAILABLE`, `CAPABILITY_RECORDS_UNAVAILABLE`, `SERVICE_STOPPING` |
| 500 | `INTERNAL_ERROR` |

Job errors (`PARTIAL_RECORDING`, `EXPORT_FAILED`, `JOB_INTERRUPTED`, `JOB_CANCELLED`, `LOGIN_REQUIRED`) are carried in a successful HTTP job-status response, not inferred from the polling HTTP status.

The default store is `output/continuous-jobs/`. Embedded callers can use `createServer({port, session, exports:{outputRoot, python, ffmpeg}, createRanges})`; the export root must remain below repository `output/`. It is one store per resident service process. After closing the HTTP server, await `server.shutdown()` to finish owned job cleanup before closing authentication or exiting. The standalone entry point does this on termination signals.

Validation boundary: HTTP tests use an injected account inventory and capture transport. Configured media tests run real PyAV/FFmpeg through the resident HTTP service, including full decode. They do not claim a new HomeBase hardware acceptance run.
