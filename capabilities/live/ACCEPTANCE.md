# Opt-in real HomeBase acceptance

**Current result: NOT RUN.** No authorized account/LAN/HomeBase is available in the implementation environment. Offline tests are not hardware PASS. No new `liveVideo`, talkback or RTSP verification has been saved.

1. On the authorized HomeBase LAN, install dependencies/build with Node 24 (`npm ci`, `npm run setup`, `npm run build`), install FFmpeg with H264 decoding and `libx264`, and run `npm start`. Sign in locally through the existing interface. Use an idle T8600/PROFESSIONAL_247 camera attached to T8030. Do not supply credentials to the acceptance script.
2. Record the resident process ID and its UDP/FFmpeg child handles before the run using your OS tools (Linux examples: `lsof -a -p PID -iUDP`, `pgrep -a -P PID`; Windows: `Get-NetUDPEndpoint -OwningProcess PID` and the process child list). Save this privately alongside the resulting evidence. Record inventory `device_type`, exact camera serial/model/main and secondary firmware, HomeBase serial/model/main and secondary firmware, channel and LAN reachability. Unknown firmware remains unknown and does not satisfy this acceptance.
3. Explicitly opt in, substituting the actual camera serial and executable path:

   ```sh
   EUFY_LIVE_HARDWARE_ACCEPTANCE=1 EUFY_LIVE_CAMERA_SERIAL=YOUR_CAMERA_SERIAL EUFY_FFMPEG=/path/to/ffmpeg node capabilities/live/acceptance.cjs
   ```

   On PowerShell, set those environment variables with `$env:NAME='value'` before running `node capabilities/live/acceptance.cjs`. `EUFY_LIVE_ORIGIN` optionally selects another loopback resident port. The runner writes a unique private directory below `output/live-acceptance/`, prints its path, starts only that camera, attaches media immediately, retains 10 seconds of media, explicitly stops, waits for HTTP EOF, fully decodes **every video frame** with `ffmpeg -xerror -i sample.mp4 -map 0:v:0 -f null -`, and records before/after status. A nonzero result means incomplete acceptance. It never updates the capability store.
4. Inspect `acceptance.json`, `sample.mp4` and `decode.stderr.log`: observed start command 1003 via outer 1350, exact channel, successful acknowledgment, actual media byte arrival, actual input video/audio codec values, full-decode exit 0, stop1004 acknowledgment, `cleanupComplete: true`, no error. Record UTC time and any observed firmware values that were initially absent. Retain the sample; viewing a first frame or probing headers is insufficient.
5. Repeat same-ID start and same-ID stop and inspect identity/command counts. Repeat with a new request ID, with the media client terminated, with no media attachment (10-second bound), and with resident shutdown while media is attached. Compare UDP/child handles to step 2, confirm no dedicated replacement socket/FFmpeg child and no continuing camera live indication. Start historical playback/export first and confirm live returns `SERVICE_BUSY`; start live first and confirm historical/range/legacy/session replacement cannot preempt it. Do not deliberately take down other users' work. Offline/rejection/media timeout are fault-injection covered; only record real failure cases that can be safely arranged on the authorized device.
6. After reviewing all evidence, an operator may record **only `liveVideo`** as verified using the existing [DeviceVerificationRepository](../devices/verification-store.cjs) / [verification procedure](../devices/VERIFICATION.md). Use the exact `verificationScope` from this run, a dated evidence source pointing to the retained acceptance directory, and an outcome describing media arrival, full decode, stop and cleanup. Record only complete observations. A changed camera, firmware, HomeBase or channel does not inherit this record. Do not update talkback or RTSP from live-video evidence.
